4. IMPLEMENTATION STRATEGY
===============================================================================

Split into 3 sub-features, implemented bottom-up (dependencies first):

  Sub-feature A: Activity Backend + IPC (new tables, repository, IPC handler)
  Sub-feature B: Analytics Backend + IPC (aggregation queries, IPC handler)
  Sub-feature C: Analytics Frontend (page, chart components, hooks)

Order: A → B → C

Rationale:
  - Activity backend must exist before analytics can query activity data
  - Analytics backend provides aggregation endpoints for frontend charts
  - Frontend depends on both backend subsystems being complete
  - Dashboard mock data replaced as part of analytics frontend work

### 7A. New Database Migration

  electron/migrations/002_activity_usage_tables.sql

  -- Activity Logs table
  CREATE TABLE IF NOT EXISTS activity_logs (
      id INTEGER PRIMARY KEY AUTOINCREMENT,
      entity_type TEXT NOT NULL,
      entity_id INTEGER,
      entity_name TEXT DEFAULT '',
      action TEXT NOT NULL,
      details TEXT DEFAULT '',
      created_at TEXT DEFAULT (datetime('now'))
  );

  -- Usage Logs table
  CREATE TABLE IF NOT EXISTS usage_logs (
      id INTEGER PRIMARY KEY AUTOINCREMENT,
      agent_id INTEGER,
      provider_id INTEGER,
      model_id INTEGER,
      project_id INTEGER,
      input_tokens INTEGER DEFAULT 0,
      output_tokens INTEGER DEFAULT 0,
      cost REAL DEFAULT 0,
      timestamp TEXT DEFAULT (datetime('now')),
      FOREIGN KEY (agent_id) REFERENCES agents(id) ON DELETE SET NULL,
      FOREIGN KEY (provider_id) REFERENCES providers(id) ON DELETE SET NULL,
      FOREIGN KEY (model_id) REFERENCES models(id) ON DELETE SET NULL,
      FOREIGN KEY (project_id) REFERENCES projects(id) ON DELETE SET NULL
  );

  -- Indexes
  CREATE INDEX IF NOT EXISTS idx_activity_entity ON activity_logs(entity_type, entity_id);
  CREATE INDEX IF NOT EXISTS idx_activity_action ON activity_logs(action);
  CREATE INDEX IF NOT EXISTS idx_activity_created ON activity_logs(created_at);
  CREATE INDEX IF NOT EXISTS idx_usage_agent ON usage_logs(agent_id);
  CREATE INDEX IF NOT EXISTS idx_usage_provider ON usage_logs(provider_id);
  CREATE INDEX IF NOT EXISTS idx_usage_model ON usage_logs(model_id);
  CREATE INDEX IF NOT EXISTS idx_usage_project ON usage_logs(project_id);
  CREATE INDEX IF NOT EXISTS idx_usage_timestamp ON usage_logs(timestamp);

### 7B. New Repositories

  electron/repositories/activity_repository.cjs
    Pattern: Follow base_repository.cjs pattern
    Extends: BaseRepository
    Table: activity_logs
    Methods:
      - log(entityType, entityId, entityName, action, details) — INSERT
      - findAllWithFilters({ entityType, action, startDate, endDate, limit, offset })
        → SELECT with WHERE clauses for each filter
      - findByEntity(entityType, entityId) → WHERE entity_type = ? AND entity_id = ?
      - getRecent(limit) → ORDER BY created_at DESC LIMIT ?
      - getStats() → SELECT COUNT by entity_type, COUNT by action
      - deleteOlderThan(date) → DELETE WHERE created_at < ?

  electron/repositories/usage_repository.cjs
    Pattern: Follow base_repository.cjs pattern
    Extends: BaseRepository
    Table: usage_logs
    Methods:
      - logUsage({ agentId, providerId, modelId, projectId, inputTokens, outputTokens, cost })
      - getUsageOverTime(timeRange, { agentId, providerId, modelId, projectId })
        → SELECT date(timestamp), SUM(input_tokens), SUM(output_tokens)
          GROUP BY date(timestamp) ORDER BY date
      - getCostOverTime(timeRange, filters)
        → SELECT date(timestamp), SUM(cost) GROUP BY date(timestamp)
      - getCostByProvider(timeRange)
        → SELECT provider.name, SUM(cost) JOIN providers GROUP BY provider_id
      - getCostByModel(timeRange)
        → SELECT model.name, SUM(cost) JOIN models GROUP BY model_id
      - getCostByProject(timeRange)
        → SELECT project.name, SUM(cost) JOIN projects GROUP BY project_id
      - getUsageByModel(timeRange)
        → SELECT model.name, SUM(input_tokens), SUM(output_tokens) JOIN models GROUP BY model_id
      - getTokenDistribution(timeRange)
        → SELECT input_tokens, output_tokens per record for histogram

9. DATA FLOW
===============================================================================

### Activity Flow

  Entity CRUD (e.g., create agent)
    → IPC handler calls activityRepository.log('agent', id, name, 'created', '')
    → INSERT INTO activity_logs
    → Activity page / RecentActivityWidget queries activity:list
    → activityRepository.findAllWithFilters()
    → SELECT with WHERE clauses
    → Returns filtered activity list

### Analytics Flow

  Analytics page loads
    → useUsageOverTime(30) fires
    → analyticsApi.usageOverTime(30, {})
    → IPC → usageRepository.getUsageOverTime(30, {})
    → SELECT date(timestamp), SUM(input_tokens), SUM(output_tokens)
      FROM usage_logs
      WHERE timestamp >= date('now', '-30 days')
      GROUP BY date(timestamp)
      ORDER BY date
    → Returns [{date, inputTokens, outputTokens}, ...]
    → UsageTrends renders LineChart

  Cost analysis loads
    → useCostByProvider(30) fires
    → analyticsApi.costByProvider(30)
    → IPC → usageRepository.getCostByProvider(30)
    → SELECT p.name, SUM(u.cost)
      FROM usage_logs u
      JOIN providers p ON u.provider_id = p.id
      WHERE u.timestamp >= date('now', '-30 days')
      GROUP BY u.provider_id
    → Returns [{name, cost}, ...]
    → CostAnalysis renders PieChart

### Dashboard Flow

  Dashboard loads
    → UsageChartWidget calls useUsageOverTime(30)
    → Real data from IPC (replaces mock)
    → RecentActivityWidget calls useRecentActivity(5)
    → Real data from IPC (replaces mock)

10. VALIDATION AND ERROR HANDLING
===============================================================================

### Validation
  - Time range: 7, 30, 90, 365 (integer, days)
  - Activity filters: entityType (string), action (string), dateRange (ISO strings)
  - Usage log: agentId/providerId/modelId (optional integers), tokens (integers >= 0), cost (number >= 0)

### Error Handling
  - All hooks return { data, isLoading, error } from React Query
  - Charts show empty state when no data (not error)
  - Charts show loading skeleton during fetch
  - Activity list shows EmptyState when no logs
  - ErrorState with retry on API failures
  - Activity logging failures are silent (don't break CRUD operations)

### Cache Invalidation
  - Activity queries: staleTime 30 seconds
  - Analytics queries: staleTime 60 seconds
  - CRUD mutations trigger activity log → activity list auto-refreshes
  - Dashboard queries: staleTime 60 seconds (after mock removal)

### Activity Logging Strategy
  - Activity is logged AFTER successful mutations (not before)
  - Logging failures are caught and logged to console (non-blocking)
  - No activity logging for read operations (list, get)
  - Entity name stored for display (avoids joins for recent activity)
